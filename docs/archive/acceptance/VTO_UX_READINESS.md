# VTO UX and submission-readiness audit — 2026-10-18

**Latest follow-up:** device tests now ran and exposed an Android original-image authentication bug, fixed and verified below. Use the version-code-6 APK; code 5 is superseded. The original build audit below remains historical evidence.

## Shopper flow

Choose and upload a photo explicitly, then tap **Try on** once. The mobile controller journals the session/product/asset/request IDs before creating the server job or asking it to render. It automatically advances that same job and checks status every three seconds, up to 40 advances per waiting period. Completion displays the result automatically. Mock completion retains its honest no-render message.

Repeated taps are locked. Network failures stop automatic waiting; Resume/Refresh reconciles the existing job and retains the request ID. An ambiguous create with no visible server job requires explicit resume, using the original request ID. A lost submission response never creates a replacement job. The existing backend submission claim, reservation ledger and terminal cache remain authoritative. No backend contract, provider retry, budget, catalog identity/price, ranking or registration changed.

**Stop waiting** cancels local timers only and explicitly says a submitted render may continue. Navigation/background stop local polling; return/foreground can resume the same active job. Restart loads IDs from the private app journal and reads owned server state. A queued job is automatically advanced only when that journal records the earlier explicit render request. Legacy queued jobs require a Try on tap; processing jobs can be checked without another submission. Completed/failed jobs never automatically start over. Storage corruption or a failed journal write blocks new execution.

Photo upload retries retain the same upload ID and bytes in memory. Image bytes are not added to the durable journal. If the app terminates during an uncommitted upload, the shopper may need to choose the photo again; this cannot trigger a render. Orphan uploads remain subject to existing manual retention/cleanup procedures.

## Result inspection

Completed output has tap-to-expand and an explicit Expand button. The modal provides full-image fit, accessible Zoom in/out controls from 100% to 400%, horizontal/vertical scrolling, and Android Back/Back to try-on dismissal. This is display scaling only: the genuine result bytes are not altered or synthesized. Copy explains that digital zoom adds no detail.

Original/Virtual try-on buttons switch clearly labeled views. The original is fetched only when requested, through the existing owned asset metadata/content routes with the guest Authorization header. The content endpoint is `private, no-store`; original URLs are not made public. A failed original does not prevent viewing the result. Expired output is no longer loaded and cannot silently trigger a new paid render. No share/download/personal-image export was added. The journal stores IDs only, never private URLs, credentials or photo bytes; platform image rendering may use transient memory/cache subject to existing native behavior.

## Security and spending findings

- Production `/health` and `/ready` returned HTTP 200 over certificate-validated HTTPS. Readiness reported PostgreSQL/S3, OpenAI and live YouCam with PostgreSQL judge ledgers. These read-only probes invoked neither provider and do not expose budget amounts or prove remote environment values.
- OpenAI reservations precede calls; failed/unknown usage stays reserved. Durable diagnostics/receipts prevent paid replay after uncertain persistence. `OPENAI_MAX_ATTEMPTS=1` remains the required deployed setting, unchanged and not inferred from readiness.
- YouCam reserves by job ID before paid task submission. A persisted submission claim prevents replay while its outcome is unknown. Poll failures retain the task, and no automatic POST resubmission is introduced. Client retries reuse identifiers.
- Owner checks remain on sessions, jobs, upload metadata and original bytes. The new original-source client validates session/asset identity before constructing an authenticated source. Existing byte hashes/MIME decoding and size limits remain enforced.
- Private S3 keys remain server-side. Signed product access and provider output access expire. Result expiry does **not** delete the uploaded original or S3 object. Backend DeleteObject is unavailable; no automatic deletion or cleanup claim was added. Manual platform cleanup and retention policy remain operational responsibilities.
- The native external-link hook rejects malformed escapes/UTF-8 and links over 2,048 characters before Expo Router query parsing, addressing the reachable decoder risk described below without replacing Expo dependencies.
- Release remains non-debuggable, backup disabled, cleartext disabled, ARM64 only, signed with the same release certificate. Embedded Hermes JavaScript points to production HTTPS, with no emulator/loopback API URL or configured server credential values.
